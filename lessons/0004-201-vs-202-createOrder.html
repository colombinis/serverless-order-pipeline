Lección 4: 201 vs 202 — ¿qué código devuelve createOrder?

Misión · Recursos · Lección 1 · Cheatsheet de códigos HTTP

Caso real

Esta lección nace de una pregunta tuya sobre la Lección 1: «createOrder devuelve 201, pero ¿no debería ser 202?». La respuesta corta es: 202 es defendible, pero 201 es el código literalmente correcto aquí — porque el handler sí crea un recurso antes de responder. El comentario del código (que habla de un 202-style flow) es el que está flojo, no la decisión.

Las dos definiciones, sin adornos

Antes de decidir, mira qué dice la especificación. Estas no son opiniones: son definiciones de HTTP.

CódigoQué afirmaCuándo se usa
201 Created La petición produjo la creación de un recurso. El recurso ya existe cuando llega la respuesta. El servidor creó algo identificable y puede señalarlo (por URL o Location).
202 Accepted La petición fue aceptada para procesar, pero el procesamiento no terminó (o no empezó). No hay garantía de que se complete. El trabajo lo hace otro proceso/servidor, o se procesa por lotes. Es un código no comprometido.

El texto exacto de la especificación: 201 significa que «the HTTP request has led to the creation of a resource» y que «the new resource ... is created before the response is returned». 202 es «non-committal» — «there is no way to later send an asynchronous HTTP response to indicate the outcome». Fuente: MDN 201 y MDN 202, ambas citando la RFC 9110.

El discriminador

La pregunta que decide todo es una sola: ¿el servidor creó un recurso identificable antes de responder? Si sí → 201. Si el recurso todavía no existe y solo se encoló trabajo → 202.

Qué hace exactamente este handler

Mira el código real de src/handlers/createOrder.js. Hay tres cosas que ocurren antes del return:

const order = { orderId, customerId, items, status: 'PENDING', createdAt: now, updatedAt: now };

await docClient.send(new PutCommand({ TableName: process.env.ORDERS_TABLE, Item: order }));   // 1) crea el recurso
await sqsClient.send(new SendMessageCommand({ QueueUrl: ..., MessageBody: JSON.stringify({ orderId }) })); // 2) encola

return response(201, { orderId, status: order.status });   // 3) devuelve su identificador

El handler crea una fila real en DynamoDB (con orderId y estado PENDING) y devuelve ese orderId. Ese es exactamente el caso de uso de 201: la petición produjo un recurso nuevo, y el cuerpo lo identifica. El procesamiento pesado (Step Functions) es lo async — pero el recurso orden ya existe.

Por qué NO es 202 aquí: 202 diría «acepté tu trabajo, pero todavía no hay nada». Falso: la orden ya está persistida y el cliente puede consultarla. El estado PENDING no es «no creado» — es el estado actual de un recurso que sí existe.

El comentario flojo

En el código createOrder.js hay un comentario que dice «Returning fast here (202-style flow)». Eso describe la intención (responder rápido con procesamiento async), no el código que realmente devuelve. Confunde un patrón con un código HTTP. Patrón: sync-then-async. Código: 201. Son dos cosas distintas.

El matiz que sí pregunta el examen: invocación sync vs async

Aquí está la parte que conecta con AWS. El código de arriba devuelve un cuerpo con el orderId. Eso solo es posible porque API Gateway invoca la Lambda de forma síncrona (InvocationType: RequestResponse, el default). Si la invocación fuera asíncrona, AWS te fuerza un 202 y borra el cuerpo:

Invocación síncrona (este proyecto)Invocación asíncrona
ConfigRequestResponse (default)X-Amz-Invocation-Type: Event en la integración
Qué devuelve la API de Lambda200 + el payload de la función202 + solo el status code
Puede devolver orderId?Sí — el handler arma la respuestaNo — el cliente no recibe payload
Quién encola el trabajoEl propio handler (escribe DynamoDB + SQS)API Gateway / Lambda (fire-and-forget)

Dato de la fuente oficial: en la API Invoke de Lambda, «For the RequestResponse invocation type, this status code is 200. For the Event invocation type, this status code is 202.» (AWS — Lambda Invoke API). Y para configurar esa invocación async en API Gateway se usa el header X-Amz-Invocation-Type: Event (AWS — Set up asynchronous invocation).

El fork de diseño

Opción A (la del proyecto): la Lambda hace el enqueue y devuelve 201 con el orderId. El cliente conoce su recurso.
Opción B: API Gateway invoca la Lambda async → 202 sin cuerpo. El cliente no recibe identificador; tendría que consultar por otro canal.
Elegir entre 201 y 202 no es corregir un número: es elegir qué contrato le prometes al cliente.

Consejo de precisión: el Location que falta

Una nota fina, para que tu 201 sea de libro (y aparezca en entrevistas): la RFC pide que un 201 identifique el recurso creado — idealmente con un header Location: /orders/{orderId}. Hoy el orderId va en el cuerpo, que también sirve, pero el Location es el sello canónico. Es una mejora de una línea en src/lib/response.js.

Quiz: Comprueba tu entendimiento

¿Cuál es el discriminador para elegir entre 201 y 202?

  • Si la respuesta tarda menos de doscientos milisegundos
  • Si el servidor creó un recurso antes de responder
  • Si la petición llegó por el método POST original
  • Si el trabajo lo procesa otro microservicio interno

¿Qué devuelve AWS si API Gateway invoca la Lambda de forma asíncrona?

  • Un 200 con el cuerpo completo de la función
  • Un 201 con la ubicación del recurso creado
  • Un 202 con el status code y sin cuerpo
  • Un 204 sin cuerpo y sin identificador alguno

¿Por qué el estado PENDING no obliga a responder 202?

  • Porque PENDING es el estado de un recurso ya creado
  • Porque DynamoDB no soporta escrituras asíncronas
  • Porque SQS garantiza entrega exactamente una vez
  • Porque API Gateway reescribe todos los códigos

Lectura recomendada (fuente primaria)

Lee directamente la RFC 9110, secciones 15.3.2 (201 Created) y 15.3.3 (202 Accepted). Son dos párrafos cada una y son el árbitro final de esta discusión. Para el lado AWS, la fuente de verdad es Invoke más la invocación asíncrona.
