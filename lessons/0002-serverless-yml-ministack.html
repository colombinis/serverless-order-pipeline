Lección 2: serverless.yml y el despliegue contra MiniStack

Misión · Recursos · Lección 1

Caso real (histórico)

Mientras preparábamos esta lección, el contenedor app de este proyecto (el que corría serverless-offline en el setup anterior) estaba en crash-loop (Restarting). Lo vamos a usar como caso de estudio: aprenderás a diagnosticar exactamente este tipo de error.

¿Qué es serverless.yml?

serverless.yml es el plano único que declara toda tu infraestructura. Un solo archivo YAML dice "tengo 8 Lambdas, una tabla DynamoDB, una cola SQS, un tópico SNS y una state machine". Ese es todo el flujo de este proyecto.

La clave para la certificación: Serverless Framework no crea los recursos directamente. Convierte tu serverless.yml en un template de CloudFormation, y CloudFormation (real o emulado) es quien realmente crea cada recurso. El marco es solo un traductor que te evita escribir el template a mano.

Anatomía del archivo

Mirá el `serverless.yml` real de este proyecto mientras seguís. Prestá atención a tres detalles, porque son los que más aparecen en exámenes:

1. Las variables de entorno conectan el código con la infra

environment:
  ORDERS_TABLE: ${self:service}-orders-${self:provider.stage}
  ORDER_QUEUE_URL: ${env:ORDER_QUEUE_URL, 'https://sqs.${self:provider.region}.amazonaws.com/123456789012/${self:service}-order-queue-${self:provider.stage}'}
  NOTIFICATIONS_TOPIC_ARN: !Ref OrderNotificationsTopic
  STATE_MACHINE_ARN: !Ref OrderFulfillmentStateMachine

El código nunca hardcodea nombres de recursos. Lee process.env.ORDERS_TABLE, process.env.ORDER_QUEUE_URL, etc. El nombre real se inyecta en deploy. Esto es infraestructura como código bien hecha: si cambias el nombre de la tabla, el Lambda no se entera.

Notá las dos sintaxis: ${self:...} es la interpolación de Serverless, y !Ref / !GetAtt son funciones intrínsecas de CloudFormation que resuelven el ARN del recurso al desplegar.

Aprendizaje real (bug de esta sesión): ORDER_QUEUE_URL: !Ref OrderQueue funciona en AWS real, pero offline resuelve el Ref de la cola con una cuenta placeholder y MiniStack responde QueueDoesNotExist. La solución es el patrón ${env:VAR, fallback}: en el contenedor (docker-compose) la variable apunta a http://ministack:4566/123456789012/..., y en un deploy real cae al fallback con la URL de SQS real.

2. El IAM role del provider es "least privilege"

iam:
  role:
    statements:
      - Effect: Allow
        Action: [dynamodb:PutItem, dynamodb:GetItem, dynamodb:UpdateItem]
        Resource: !GetAtt OrdersTable.Arn

Cada Lambda recibe solo lo que necesita: PutItem/GetItem/UpdateItem en la tabla, SendMessage en la cola, Publish en el tópico, StartExecution en la state machine. Sin permisos *. Ese es el patrón least privilege que evalúan en la certificación.

3. Una función = un handler = una responsabilidad

functions:
  createOrder:
    handler: src/handlers/createOrder.handler
    events:
      - httpApi:
          path: /orders
          method: post

  validateStock:
    handler: src/handlers/validateStock.handler

La sección functions mapea nombre → archivo de código. handler: src/handlers/createOrder.handler significa "exportá la función llamada handler del archivo src/handlers/createOrder.js". Ese es el contrato entre infraestructura y código: cuando CloudFormation despliega esa Lambda, sabe qué entry point ejecutar.

¿Cómo llega el código a MiniStack?

Hay dos modos de correr este proyecto, y confundirlos es la fuente de la mayoría de los errores:

Los dos modos de ejecución de este proyecto

Modo A — deploy real (o a un emulador)

serverless deploy empaqueta el código, genera el template CloudFormation y lo envía a la API de CloudFormation. Si el SDK apunta a MiniStack (AWS_ENDPOINT_URL=http://localhost:4566), CloudFormation emulado procesa el template y crea todo adentro de MiniStack: tabla, cola, tópico, state machine, Lambdas, el role IAM e incluso un API Gateway.

Corrección verificada (Lección 3)

En la práctica, el CF de MiniStack no puede procesar el template que genera serverless: rechaza TemplateURL (pide TemplateBody inline) y no resuelve el ciclo de dependencias de las Lambda::Version. Por eso este proyecto usa scripts/ministack-bootstrap.sh para provisionar los recursos por API directa. El "Modo A" sigue siendo el camino correcto para AWS real.

Matiz importante: esto no significa que MiniStack no pueda emular API Gateway. La emulación de API Gateway (v1 REST de 86 operaciones y v2 HTTP de 42 operaciones) sí existe y funciona completa por control-plane — se crea con la AWS CLI contra :4566 (create-rest-api → create-resource → put-method → put-integration → create-deployment) y se invoca por /restapis/{apiId}/{stage}/_user_request_/. Lo que falla es solo la materialización del template de serverless a través de CloudFormation. Ver scripts/test.sh para un ejemplo funcionando.

Modo B — serverless-offline (el que usaba este proyecto)

Nota de contexto: este modo fue el camino inicial de este proyecto, pero ya no se usa — hoy la entrada HTTP es la API Gateway nativa de MiniStack (v1 REST, creada por scripts/ministack-bootstrap.sh por control-plane, invocable en /restapis/{apiId}/{stage}/_user_request_/). Se mantiene aquí por valor pedagógico: muestra cómo se veía la matriz de servicios antes del bootstrap.

El plugin serverless-offline emula en proceso el API Gateway y las Lambdas en el puerto 3000. Los servicios de backend (DynamoDB, SQS, SNS, Step Functions) no los emula: los busca en MiniStack a través de AWS_ENDPOINT_URL.

Por esto el diagrama de la Lección 1 decía 9 servicios. El API Gateway y las Lambdas los ves corriendo en el contenedor app; el resto vive en MiniStack. Dos contenedores, una sola arquitectura.

Cómo MiniStack "sabe" a qué servicio va cada petición

MiniStack corre los 60+ servicios en un solo puerto (4566). No hay un puerto por servicio. Enruta la petición así (documentación oficial):

  • Por el scope del header de autorización (la firma SigV4 incluye el nombre del servicio)
  • Por el header X-Amz-Target (servicios JSON como DynamoDB, SNS, Step Functions)
  • Por el path de la URL (servicios REST como S3)

Por eso tu código no cambia si el servicio está en AWS real o en MiniStack: el SDK firma los headers igual, y MiniStack los lee igual. El único cambio es --endpoint-url (CLI) o AWS_ENDPOINT_URL (SDK).

Dónde verificar los errores: las 3 capas

Cuando algo falla, hay exactamente tres lugares donde mirar, en este orden:

Capa 1 — El contenedor

docker compose logs -f ministack. Ahí salen los logs de las Lambdas (los workers de MiniStack), los eventos del Event Source Mapping SQS y cualquier crash del emulador. Un comando que sirve: docker compose logs ministack | grep ESM.

Capa 2 — CloudWatch Logs (emulado)

MiniStack emula CloudWatch Logs en el :4566. serverless logs -f createOrder -t consulta un CloudWatch emulado para traer los logs del handler. En AWS real es el mismo comando.

Capa 3 — El estado de los recursos

¿Existe la tabla? ¿La cola? ¿La state machine? Se consulta directo contra MiniStack con la AWS CLI usando --endpoint-url http://localhost:4566.

Caso de estudio: el crash del contenedor app (histórico)

Este caso documenta un fallo del setup anterior (contenedor app + serverless-offline), que es el que motivó el bootstrap actual. El contenedor app ya no existe en el proyecto; el aprendizaje (leer el error en capas, matriz de versiones) sigue siendo válido.

Ahora apliquemos las capas al fallo real:

Paso 1 — Capa 1: ver los logs del contenedor (diagnóstico)

docker compose ps
# CONTAINER   SERVICE   STATUS
# app         app       Restarting (1) 5 seconds ago   ← crash-loop

docker logs serverless-order-pipeline-app 2>&1 | tail -20

El log mostraba repetidamente:

Error [ERR_REQUIRE_ESM]: require() of ES Module
/app/node_modules/serverless-offline/src/index.js not supported.
Instead change the require of index.js in null to a dynamic import()
which is available in all CommonJS modules.

Paso 2 — Leer el error con los ojos de la certificación

El error dice ERR_REQUIRE_ESM. Descomponé lo que pasa:

  • El paquete serverless-offline@13.x se publicó como módulo ES ("type": "module" en su package.json)
  • Node.js 18.x no puede hacer require() de un módulo ES — esa capacidad se habilitó por defecto en Node 20.19 y 22.12
  • Serverless Framework 3 carga los plugins con require(), así que el plugin se rompe al cargarse

Diagnóstico equivocado que evitarías

No es un problema de tu código, ni de serverless.yml. Es un problema de matriz de versiones: plugin ESM + Node viejo. En la certificación, "matriz de versiones incompatible" es una distractor típico.

Paso 3 — Capa 3: verificar el estado de MiniStack

Incluso con la capa 1 resuelta, confirmamos que MiniStack está vacío (nunca se desplegó el stack):

aws --endpoint-url http://localhost:4566 dynamodb list-tables        # []
aws --endpoint-url http://localhost:4566 sqs list-queues             # []
aws --endpoint-url http://localhost:4566 stepfunctions list-state-machines  # []

El contenedor app corría en modo offline: ese modo arrancaba las Lambdas en el puerto 3000, pero no creaba tabla, cola, tópico ni state machine. Esos tenían que existir ya en MiniStack. Hoy esa capa HTTP la cubre la API Gateway nativa que crea el bootstrap.

Quiz: Comprueba tu entendimiento

¿Qué ocurre realmente al ejecutar serverless deploy?

  • Se genera y aplica un template CloudFormation
  • Se compila el código de todas las funciones
  • Se inician contenedores emulados en local
  • Se publican los logs en CloudWatch

En este proyecto, ¿qué emula serverless-offline?

  • Todos los servicios de la arquitectura
  • API Gateway y Lambda solamente
  • Solo las funciones de los handlers
  • CloudWatch Logs de cada función

¿Cómo enruta MiniStack cada petición a su servicio?

  • Por scope de auth, X-Amz-Target o el path
  • Por un subdominio distinto por servicio
  • Porque cada servicio usa un puerto
  • Por el nombre del bucket en la URL

Un servicio de docker-compose está en "Restarting". ¿Dónde mirás primero?

  • En la consola de CloudWatch real
  • En las tablas de MiniStack con la CLI
  • En los logs de ese contenedor (docker compose logs <servicio>)
  • En el panel de DynamoDB Admin
