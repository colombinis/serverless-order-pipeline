Lección 1: Arquitectura del Pipeline de Órdenes

Lección 1 de ∞ · Misión · Recursos

El mapa antes del territorio

Antes de profundizar en cada servicio, necesitas ver el bosque completo. Este proyecto es un pipeline de procesamiento de órdenes construido con 9 servicios AWS. Cada servicio tiene un rol preciso, y el orden en que se conectan no es arbitrario — resuelve problemas reales de concurrencia, tolerancia a fallos y acoplamiento.

Vamos a recorrer el flujo completo de una orden, desde que el cliente hace POST hasta que recibe la notificación.

Diagrama de Arquitectura

Flujo completo: HTTP → Lambda → SQS → Step Functions → SNS

El flujo en 6 pasos

Cada petición HTTP recorre este camino. Vamos paso a paso:

1. El cliente envía POST /orders

Amazon API Gateway (HTTP API v2) recibe la petición. API Gateway actúa como la puerta de entrada: autentica, valida el formato HTTP, y reenvía a Lambda. En este proyecto solo hay un endpoint (POST /orders), pero en producción podrías tener cientos.

Concepto clave para certificación: HTTP API v2 es más barata y rápida que REST API v1, pero no tiene caching, WAF integration, ni API keys nativos. Elige según tus necesidades.

2. createOrder escribe en DynamoDB y envía a SQS

El Lambda createOrder hace dos cosas: escribe la orden con estado PENDING en DynamoDB, y envía el orderId a SQS. Devuelve HTTP 201 inmediatamente — el procesamiento real es asíncrono.

¿Por qué no procesar directamente? Si el Lambda procesara la orden completa, el cliente tendría que esperar 10-30 segundos (o más). Al devolver 201 y procesar async, el cliente obtiene respuesta en <200ms. SQS absorbe picos de tráfico sin perder mensajes.

3. processOrder lee SQS y arranca Step Functions

Otro Lambda (processOrder) está conectado a SQS como event source. Por cada mensaje, invoca una ejecución de Step Functions pasando el orderId. El batchSize: 1 en la configuración garantiza un mensaje → una ejecución.

4. Step Functions orquesta 5 pasos secuenciales

AWS Step Functions ejecuta una máquina de estados que coordina el cumplimiento de la orden:

EstadoQué haceServicio AWS
ValidateStockVerifica que no haya items con cantidad > 100Lambda → DynamoDB
ReserveInventorySimula reserva de inventarioLambda → DynamoDB
ChargePaymentSimula cobroLambda → DynamoDB
ConfirmOrderMarca orden como CONFIRMEDLambda → DynamoDB
NotifyCustomerPublica confirmaciónLambda → SNS

Los primeros 3 estados tienen un bloque Catch: si cualquiera falla, el flujo se desvía a CancelOrder en lugar de abortar silenciosamente.

5. CancelOrder: el fallback

Si ValidateStock, ReserveInventory o ChargePayment fallan, Step Functions ejecuta CancelOrder: actualiza DynamoDB a CANCELLED y publica una notificación de cancelación vía SNS.

6. SNS notifica al mundo exterior

Amazon SNS publica mensajes a un topic. En producción, suscribirías emails, SMS, Lambda, o WebHook aquí. En este proyecto, SNS es el punto de extensibilidad — agregar un nuevo consumidor no requiere modificar ningún código existente.

Quiz: Comprueba tu entendimiento

¿Qué hace createOrder después de recibir la petición HTTP?

  • Procesa la orden completa y devuelve 200
  • Escribe en DynamoDB y envía a SQS, devuelve 201
  • Envía a Step Functions y espera la respuesta
  • Solo guarda en DynamoDB y devuelve 201

¿Cuál es el beneficio principal de usar SQS entre createOrder y processOrder?

  • Desacoplamiento async y absorción de picos de tráfico
  • Encriptación de mensajes entre servicios
  • Reducir el costo de Lambda ejecutando menos instancias
  • Permitir que múltiples clientes escriban simultáneamente

¿Qué pasa si ChargePayment falla en Step Functions?

  • La máquina de estados se detiene y la orden queda en PENDING
  • Step Functions reintenta automáticamente 3 veces
  • Se ejecuta CancelOrder: DynamoDB se actualiza a CANCELLED y SNS publica
  • Se reinicia la máquina desde ValidateStock

Concepto clave: sync vs async

Patrón

Este proyecto usa un patrón sync-then-async: el HTTP response es síncrono (rápido), pero el procesamiento real es asíncrono (SQS + Step Functions). Este es el patrón más común en serverless y aparece en casi todos los exámenes AWS.

La clave para la certificación: Lambda + SQS = desacoplamiento. Lambda + Step Functions = orquestación. Lambda + SNS = notificación fan-out. Cada combinación resuelve un problema diferente.
