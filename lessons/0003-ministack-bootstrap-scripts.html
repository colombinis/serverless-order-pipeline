Lección 3: Bootstrap local con scripts — por qué MiniStack ignora el deploy de serverless

Misión · Recursos · Lección 1 · Lección 2

Caso real

Esta lección nace de una pregunta tuya después de que npm run deploy:local chocara contra dos muros: "no podemos reemplazar serverless por scripts que inicialicen los recursos?". Respuesta corta: sí — y para el emulador es la vía correcta, además de la única que lo deja funcionar de punta a punta.

Bajamos de la nube: los 3 muros verificados de CloudFormation en MiniStack

En la Lección 2 vimos el Modo A ("deploy real o a un emulador crea todo adentro de MiniStack"). Esa expectativa era optimista. Lo que comprobamos en vivo:

Paso que intentamosErrorQué significa
serverless deploy contra :4566The CloudFormation template is invalid: TemplateBody is requiredServerless sube el template a S3 y llama a CF con TemplateURL; el CF de MiniStack solo acepta el template inline (TemplateBody)
Volcarlo inline con --template-bodyCircular dependency detectedEl CF del emulador no resuelve el grafo de dependencias entre Lambda::Version, Lambda::Permission, la integración del API Gateway y el role IAM (AWS real sí lo hace)
Cambiar SDK v2 por SDK v3 fácilmentesolo endpoint explícitoEl framework usa aws-sdk v2, que ignora AWS_ENDPOINT_URL; ni el config file lo salva (solo la opción endpoint)

Conclusión que importa para la certificación

Los dos primeros muros no son bugs tuyos ni de serverless: son la frontera del CloudFormation del emulador ante el template de serverless. MiniStack/LocalStack emulan las APIs de los servicios (DynamoDB, SQS, SNS, Step Functions, Lambda, S3) y el control-plane de API Gateway —create-rest-api, put-method, put-integration, create-deployment, 86 operaciones REST v1 y 42 de HTTP v2—, pero su CF no materializa el template que genera Serverless Framework. Por eso su documentación recomienda explícitamente crear los recursos por API directa (aws --endpoint-url, awslocal o un SDK), igual que harías un script en AWS real con boto3/CLI.

Matiz verificado contra la doc oficial (2026)

MiniStack sí emula API Gateway completo, desde el control-plane hasta la invocación: se crea la API por AWS CLI contra :4566 y se ejecuta por http://localhost:4566/restapis/{apiId}/{stage}/_user_request_/. De hecho el propio bootstrap crea la REST API del proyecto (POST /orders → createOrder). No existe ningún servidor HTTP "alternativo" en el setup: el "muro" real es solo la materialización del template de serverless a través de CF, no la emulación del servicio API Gateway.

El patrón del script: provisionar directo con los nombres del yml

El script scripts/ministack-bootstrap.sh hace exactamente eso, en 10 pasos numerados:

  1. Empaquetar el código a un zip con zip nativo (sin Serverless Framework): replica el árbol del repo (src/ + node_modules + package.json).
  2. Subir el zip a un bucket S3 del emulador (clave con timestamp; así el update-function-code apenas referencia un objeto).
  3. Tabla DynamoDB → serverless-order-pipeline-orders-dev, PAY_PER_REQUEST.
  4. Cola SQS → -order-queue-dev, VisibilityTimeout 60.
  5. Tópico SNS → -notifications-dev.
  6. State machine OrderFulfillmentStateMachine — con el Amazon States Language igual al del yml, pero con los ARN de las Lambdas ya resueltos.
  7. Las 8 Lambdas, con nombre service-stage-función (el mismo que usa Serverless) y handler src/handlers/<nombre>.handler.
  8. Event Source Mapping SQS → processOrder (el equivalente a events: sqs del yml, que offline ignora).
  9. API Gateway rest v1 real (control-plane vía AWS CLI): create-rest-api serverless-order-pipeline-dev, resource /orders, put-method POST, integración AWS_PROXY a createOrder, y create-deployment al stage dev.
  10. Smoke test: hace un POST /orders real por la API recién creada y valida que el state machine deja la orden en CONFIRMED.

Cada recurso usa el mismo nombre que declara serverless.yml. El yml sigue siendo la fuente de verdad para AWS real; el script solo lo "ejecuta" contra el emulador por el atajo que CF local no soporta.

Idempotencia: los probes nativos, no los greps

# Patrón del script: "existe? -> skip, sino -> crea"
if aws --endpoint-url "$EP" dynamodb describe-table --table-name "$TABLE" >/dev/null 2>&1; then
  echo "ya existe"
else
  aws --endpoint-url "$EP" dynamodb create-table \
    --table-name "$TABLE" --attribute-definitions AttributeName=orderId,AttributeType=S \
    --key-schema AttributeName=orderId,KeyType=HASH --billing-mode PAY_PER_REQUEST
fi

Detalle que aprendimos a golpes: MiniStack responde mal los filtros JMESPath tipo [?stateMachineArn==...] y comparar URLs de cola por host (localhost vs ministack) da falsos negativos. Por eso el script usa probes nativos — describe-table, get-queue-url, get-topic-attributes, describe-state-machine — que devuelven éxito solo si el recurso existe. Correr el script dos veces no borra ni duplica nada.

Por qué es MEJOR para MiniStack: habilita lo que offline no puede

El argumento fuerte no es solo "funciona": es que con el bootstrap el pipeline se vuelve event-driven de verdad. Comparación del mismo recurso en los dos modos:

Recurso/eventoserverless offlineBootstrap en MiniStack
HTTP POST /ordersAPI Gateway en proceso (:3000, solo HTTP+Lambda)API Gateway real de MiniStack (_user_request_/orders) → Lambda
Invocación de la Lambdaen el proceso de Nodemismo código, pero en un runtime contenedor real de MiniStack
Consumo de SQSNO — el mensaje queda en la colaEvent Source Mapping firma el mensaje y dispara processOrder solo
Step Functions Tasksno ejecuta ninguna taskejecuta las 5 tasks, cada una con su worker (cold start ≈5–6 s)
Publicación SNSsolo código, sin confirmación de entrega realpublish real contra el tópico del emulador
El mismo dato que ya tenías, visto desde el ángulo correcto: serverless-offline solo emula la mitad frontal (HTTP + Lambda en proceso). El backend asíncrono (SQS, SFN, SNS) que es el corazón de esta arquitectura queda "muerto" en offline. El bootstrap lo enciende sin salir de la máquina.

Así se ve el pipeline completo (el que el examen pregunta)

El flujo completo ahora: la API Gateway real de MiniStack dispara la Lambda; SQS (Event Source Mapping), SFN y SNS viven en MiniStack y se disparan solos. Todo el servicio HTTP y el backend asíncrono son emulados por MiniStack — no hay ningún servidor Express en el setup.

Comandos para verlo con tus propios ojos

./scripts/ministack-bootstrap.sh      # crea tabla/cola/tópico/SFN + 8 Lambdas + ESM + API Gateway (idempotente)
                                      # imprime al final: API_URL=http://localhost:4566/restapis/<apiId>/dev/_user_request_/orders

curl -X POST "$API_URL" \
  -H "Content-Type: application/json" \
  -d '{"customerId":"mini-user","items":[{"sku":"ABC","qty":2}]}'

aws --endpoint-url http://localhost:4566 stepfunctions list-executions \
  --state-machine-arn arn:aws:states:us-east-1:123456789012:stateMachine:OrderFulfillmentStateMachine \
  --query 'executions[].status'

aws --endpoint-url http://localhost:4566 dynamodb get-item \
  --table-name serverless-order-pipeline-orders-dev \
  --key '{"orderId":{"S":"<el-id-de-la-respuesta>"}}' --query 'Item.status.S'

docker compose logs ministack | grep ESM       # "processed 1 SQS messages"

Mirá dos detalles en ese grep: MiniStack registra "ESM: Lambda processed 1 SQS messages" — es la prueba de que el evento SQS se disparó solo, sin que nadie lo llame. Y los 5 Tasks del state machine aparecen en los logs como Lambda worker spawned, cada uno con su cold start.

Límites honestos (para no llevarte sorpresas al examen)

  • IAM no existe en el emulador: los roles son ARNs dummy y MiniStack no valida permisos. El concepto de least privilege (que sí evalúa la certificación) solo se prueba en AWS real — local es puro comportamiento funcional.
  • Confirmá que "serverless.yml es la fuente de verdad, no el script": si para AWS real cambias el yml, el script local queda desalineado hasta que lo actualices a mano. En producción el deploy es serverless; el bootstrap es solo el "juguete local".
  • El zip del bootstrap copia node_modules completa (y hasta .opencode/): 41 MB. Sirve para probar, pero un empaquetado limpio (solo src/ + dependencias de producción) es lo que haría serverless en AWS real — buen tema para una próxima lección.
  • Cold starts reales, sin capa de caché: cada task arranca su contenedor (≈5–6 s). En AWS esto se mitiga con provisioned concurrency/ceiling; acá te sirve para explicar el timing de un workflow.

Ejercicio: cerrá el círculo sola/solo

  1. Corré ./scripts/ministack-bootstrap.sh y fijate qué dice "ya existe" (idempotencia). También queda el comandito curl "$API_URL" que imprime al final.
  2. Creá una orden con curl y anotá su orderId.
  3. Consultá la ejecución del state machine hasta que figure SUCCEEDED.
  4. Consultá el status de la orden en DynamoDB: debería terminar en CONFIRMED.
  5. Pregunta trampa: ¿por qué al consultar a los 4 segundos viste STOCK_VALIDATED y no CONFIRMED? (mirá el cold start de los Tasks)

Cuando lo corras, contame qué viste. Si querés, probamos al final el update-function-code: cambiás una línea de un handler, volvés a correr el bootstrap y el cambio pega sin recrear la función.

Quiz: Comprueba tu entendimiento

¿Por qué `serverless deploy` no puede materializar el stack contra MiniStack?

  • Su CloudFormation no soporta TemplateURL ni la estructura del template generado
  • Porque MiniStack requiere Java instalado
  • Porque las Lambdas se ejecutan con el SDK v2
  • Porque exige credenciales IAM reales

¿Qué habilita el bootstrap que serverless-offline no puede hacer?

  • Emular el endpoint HTTP con un servidor local
  • Que SQS dispare processOrder y Step Functions ejecute las Tasks
  • Comprimir el código y subirlo a S3 del emulador
  • Generar el template CloudFormation a partir del yml

¿Cómo detecta el script si un recurso ya existe en MiniStack?

  • Con probes nativos que fallan si no existe (describe-table, get-queue-url, etc.)
  • Comparando URLs completas de cada servicio
  • Con filtros JMESPath sobre list-*
  • Creando el recurso y capturando el error de duplicado

Sobre los roles IAM al registrar Lambdas en MiniStack:

  • Se validan contra políticas reales del yml
  • Son ARNs dummy: el emulador no verifica permisos
  • Solo se validan para la cola SQS
  • Requieren una policy en el mismo template CF

Cierre

Ya tenés el pipeline vivo y reproducible: ./scripts/ministack-bootstrap.sh + curl "$API_URL" + el state machine lo deja en CONFIRMED. En los trabalenguas que quedan: empaquetado limpio del zip (layer/esbuild), o replicar el mismo script en Python/boto3 si te sirve para el portfolio.
