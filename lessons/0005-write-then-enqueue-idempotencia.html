Lección 5: El fallo clásico del patrón — write-then-enqueue e idempotencia

Misión · Recursos · Lección 4 · Cheatsheet: idempotencia

Caso real

En la Lección 4 quedó la pregunta en el aire: «si createOrder escribe DynamoDB y después SQS, ¿qué pasa si el envío a SQS falla pero la escritura ya ocurrió?». Spoiler: en este proyecto pasaría algo malo, y el código lo demuestra. Esto es el fallo clásico del patrón sync-then-async y material de examen garantizado.

Estado: fixes aplicados

Las curas A y C ya están en el código real: createOrder con idempotency key (orderId determinístico + condición attribute_not_exists) y processOrder con nombre de ejecución determinista + deglución de ExecutionAlreadyExists. 14 tests pasan. La cura B (outbox) queda como siguiente paso. Detalles en learning-records/0009.

Las dos mitades del problema

Esto parece una sola cosa, pero son dos problemas distintos con dos curas distintas:

ProblemaPreguntaEjemplo
Consistencia ¿Quedan los estados coherentes si algo falla a mitad de camino? La orden quedó guardada (PENDING) pero el evento para procesarla nunca llegó → orden huérfana para siempre.
Idempotencia ¿Re-ejecutar la misma operación produce el mismo resultado, sin efectos duplicados? El cliente reintenta el POST, o SQS redelivera el mensaje → dos cargos, dos órdenes, dos confirmaciones.

El principio 7 del AWS Well-Architected — Serverless Applications Lens lo dice literal: «Design for failures and duplicates: operations triggered from requests or events must be idempotent, as failures can occur and a given request or event can be delivered more than once».

Inventario de fallos en el código real

Punto de falloQué hace el código hoyConsecuencia
PutCommand OK, SendMessage falla createOrder lanza y API Gateway responde error (502 con proxy integration). La fila PENDING ya quedó escrita. Orden huérfana: nadie la va a procesar jamás. Es el fallo de consistencia.
El cliente reintenta el POST Cada POST genera orderId = uuidv4() nuevo. No hay key de idempotencia. Orden duplicada. El retry de un cliente no recibe la orden original: crea otra.
SQS redelivera un mensaje La cola es estándar: «at-least-once ... more than one copy of a message might be delivered» (fuente: SQS standard queues). Visibility timeout 60 s: si el consumidor falla, el mensaje vuelve. El mismo orderId puede procesarse dos veces.
processOrder arranca la ejecución name: \`order-\${orderId}-\${Date.now()}\` — nombre único por llamada. Redelivery = ejecución nueva → el workflow completo corre dos veces → doble cargo.
Los Tasks actualizan estado updateOrderStatus hace un UpdateCommand sin ConditionExpression (actualización ciega). Re-ejecutar un paso no encuentra ninguna barrera.

El punto fino que el examen adora: StartExecution ya es idempotente… si lo dejás

Aquí está la joya. La API StartExecution de Step Functions es idempotente para workflows STANDARD (que es el tipo de esta state machine): si llamás con el mismo nombre y el mismo input mientras esa ejecución está corriendo, la llamada devuelve el ARN de la ejecución ya existente en vez de crear otra. De la fuente oficial: StartExecution — «StartExecution is idempotent for STANDARD workflows. For a STANDARD workflow, if you call StartExecution with the same name and input as a running execution, the call succeeds and return the same response as the original request».

Pero el código de processOrder.js le mete Date.now() al nombre:

// Hoy (rompe la idempotencia):
name: `order-${orderId}-${Date.now()}`

// Fix de UNA línea (la deja trabajar):
name: `order-${orderId}`

Con el nombre fijo, el SQS redelivery de order-abc recibe la misma ejecución — el duplicado se absorbe gratis y de forma atómica, sin consultar la tabla. Ese es el tipo de detalle que separa una implementación correcta de una excelente.

Los límites de la idempotencia de SFN

Solo aplica mientras la ejecución esté corriendo. Si la ejecución ya cerró (SUCCEEDED/FAILED) y llega el duplicado, StartExecution responde ExecutionAlreadyExists (400). Una ejecución cerrada no se reutiliza → ahí necesitás la cura C (consumidor con guardas), no solo el nombre fijo. La fuente lo dice: «if the execution is closed or the input is different, it returns a 400 ExecutionAlreadyExists error».

Las 3 curas del patrón

A. Idempotency key en la API (cura los duplicados del cliente)

El cliente manda una key estable (Idempotency-Key en el header o en el body). createOrder la guarda como clave (o con una condición attribute_not_exists); si llega un retry con la misma key, devuelve el mismo orderId en vez de crear otro. Es el patrón del decorador @idempotent de AWS Lambda Powertools: guarda un registro INPROGRESS → COMPLETE en DynamoDB con la key, y re-sirve la respuesta guardada mientras la ventana (1 hora por defecto) no expire. También te protege de dos POST idénticos concurrentes, que es peor que el retry secuencial.

B. Transaction outbox (cura la consistencia)

El problema raíz del fallo de consistencia es que la escritura y el enqueue son dos sistemas sin transacción. La cura canónica en serverless es el outbox: escribir la orden y el evento en la misma transacción de DynamoDB (TransactWriteItems), y que un DynamoDB Streams reenvíe los eventos a SQS.

Izquierda: el fallo actual. Derecha: el outbox — la escritura y el evento nacen y mueren juntos, atómicamente.

La ventaja del outbox es total: o la orden existe y su evento también, o no existe ninguno. Nunca hay huérfanas ni eventos perdidos. Es el patrón que AWS recomienda cuando necesitás consistencia entre un estado y un evento.

C. Consumidor idempotente (cura los duplicados de SQS)

El consumidor debe ser idempotente por las dos vías: nombre de ejecución determinista (el fix de una línea de arriba) y guardas en las escrituras — convertir updateOrderStatus en una actualización condicional, p. ej. ConditionExpression: '#status = :expected' (solo pasar de PENDING a PAYMENT_CHARGED si el estado actual es el esperado). Así una segunda corrida no re-ejecuta el cargo: el UpdateCommand falla si el estado ya cambió, y el task puede tratarlo como no-op.

Quiz: Comprueba tu entendimiento

¿Qué pasa si SendMessage falla después del PutItem en createOrder?

  • Orden huérfana PENDING y el retry del cliente duplica
  • El mensaje se pierde y la tabla queda vacía
  • La Lambda reintenta sola y al final lo logra
  • DynamoDB revierte la escritura automáticamente

¿Por qué SQS estándar puede entregar un mensaje dos veces?

  • Porque el visibility timeout siempre es cero
  • Porque garantiza exactamente una sola entrega
  • Porque garantiza al menos una entrega con copias
  • Porque los mensajes caducan a los cinco minutos

¿Qué efecto tiene `name: order-${orderId}-${Date.now()}` en processOrder?

  • Garantiza una sola ejecución por cada mensaje
  • Reutiliza la ejecución anterior para ahorrar
  • Repite la ejecución hasta que esté cerrada
  • Anula la idempotencia y duplica al redeliverar

¿Qué patrón cura el problema de consistencia write-then-enqueue?

  • Outbox con transacciones y reenvío vía streams
  • Aumentar el visibility timeout de la cola
  • Generar un uuid nuevo en cada petición
  • Desactivar los reintentos de API Gateway

Ejercicio: reproducí el duplicado con tus propias manos

  1. Levantá el entorno y corré el bootstrap: ./scripts/ministack-bootstrap.sh (idempotente).
  2. Hacé un curl -X POST "$API_URL" -H "Content-Type: application/json" -d '{"customerId":"dup","items":[{"sku":"ABC","qty":2}]}' dos veces, igualito.
  3. Anotá los dos orderId que devuelve. ¿Son iguales? Pista: no lo son — cada POST creó una orden. Ese es el duplicado del cliente: sin idempotency key, retry = nueva orden.
  4. Consultá DynamoDB: aws --endpoint-url http://localhost:4566 dynamodb scan --table-name serverless-order-pipeline-orders-dev --query 'Items[].orderId'. Hay dos filas para un solo «carrito».
  5. Fix de una línea: cambiá el name de processOrder.js a order-${orderId}, actualizá la Lambda con el bootstrap y repetí el smoke test curl. Mismo mensaje redeliverado → misma ejecución SFN → el chargePayment corre una sola vez por orden.

Después del ejercicio contame qué viste en las dos corridas antes y después del fix. Si querés, atacamos el siguiente nivel: agregar la idempotency key a createOrder con su test, o implementar el outbox con TransactWriteItems + Streams.
